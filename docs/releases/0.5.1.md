# AIXEM 0.5.1

## Overview

AIXEM 0.5.1 makes the documentation sufficient for an AI agent to author component definitions, draw symbol graphics, bind semantic properties and ports, place instances, route nets, render evidence, diagnose defects, and repair the authoritative source without normal renderer-code archaeology.

> **Document ID:** `AIXEM-RELEASE-051-001`  
> **Status:** Informative  
> **Version:** 1.0

## Release scope

The release preserves the route-first architecture, authority boundaries, deterministic generation, and compatibility surface introduced by 0.5.0. It closes the authoring-sufficiency gap through explicit contracts and executable examples.

Delivered capabilities include:

- a normative renderer contract for field, variant, parameter, port, transform, style, and output resolution;
- a normative symbol design profile with measurable grid, lead, port, pitch, field, and grouping rules;
- a component-symbol binding contract for `asset`, `portMap`, `fieldMap`, and `defaultVariant`;
- symbol, schematic, and routing cookbooks;
- an agent-readable `.aixsym` field reference;
- complete documentation coverage for all 13 supported graphics primitive types;
- explicit visible-lead versus electrical-port semantics;
- eight executable golden authoring projects and a deliberate visual-repair fixture;
- source-backed Markdown snippet drift checks;
- simple routes plus the ordered `author-component-circuit` composite workflow;
- generated task packets with source digests and stage exits;
- renderer precedence, binding failure, geometry lint, route budget, and example determinism tests;
- a fixture-backed eight-task evaluation harness with explicit execution-mode disclosure;
- three complete validation and error-improvement passes.

## Composite authoring path

```text
create-symbol
→ create-schematic
→ route-nets
→ render-review
→ validate-project
```

Each simple stage remains bounded to seven documents, 96 KiB, and depth three. Outputs from one stage become explicit inputs to the next stage rather than widening one unbounded search.

## Executable example set

The release includes isolated projects for:

1. two-pin passive authoring;
2. six-pin connector authoring;
3. twelve-pin IC authoring;
4. parameter and variant precedence;
5. field and port binding;
6. two-terminal orthogonal routing;
7. multi-terminal junction and unrelated crossing semantics;
8. visual lead/port defect detection and repair.

Each successful project includes locked sources, rendered SVG/workbench output, `resolved-scene.json`, and project validation evidence.

## Three refinement passes

### Pass 1 — Completeness and contract closure

The active schemas, renderer behavior, style profile, route metadata, and 0.5.0 baseline are inventoried. Every authoring-relevant field, primitive, binding rule, and runtime precedence chain receives one canonical documentation owner. Duplicate or missing contract ownership is rejected.

### Pass 2 — Agent usability and drawing quality

All authoring routes and task packets are compiled, the eight fixture-backed evaluation tasks are executed, schema and semantic closure are checked, golden renders are inspected, and ambiguous guidance is repaired. Normal simulated tasks must use no repository-wide search and no renderer-source inspection.

### Pass 3 — Release integrity and regression

Canonical and generated documentation is built twice, golden renders are repeated, the integrated 0.5.0-compatible example is rerendered, the complete repository test suite is run, visual evidence is captured, requirement evidence is regenerated, the release manifest is closed, and the deterministic ZIP is externally verified.

## Compatibility

A 0.5.0 symbol that uses only existing fields and fallback styles remains valid under 0.5.1. The release does not change semantic endpoint identity, topology authority, or project lock behavior. New task packets and composite-route metadata are derived navigation products and do not become normative authority.
